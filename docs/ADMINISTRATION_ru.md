# Администрирование TunnelSlate

Русский · [English](/docs/ADMINISTRATION_en.md) · [Быстрый старт](/docs/QUICKSTART_ru.md) · [О проекте](/docs/OVERVIEW_ru.md)

## Параметры .env

Изменяйте параметры в `.env`, затем выполняйте `docker compose up -d`.

| Настройка | Что указать |
| --- | --- |
| `TUNNELSLATE_PUBLIC_URL` | Адрес панели со схемой и, если нужен, портом. Без пути после домена. Он должен совпадать с адресом, который вы открываете в браузере. |
| `TUNNELSLATE_BASE_PATH` | Пусто для отдельного домена. Для адреса `https://control.example.com/ovpn/` укажите `/ovpn`, а в `PUBLIC_URL` — только `https://control.example.com`. |
| `TUNNELSLATE_COOKIE_SECURE` | `true` для HTTPS. Для локального HTTP-доступа — `false`. |
| `TUNNELSLATE_SESSION_TTL` | Как долго действует вход в панель. По умолчанию `12h`; допустимо от `1m` до `168h`. |
| `TUNNELSLATE_AUDIT_RETENTION_DAYS` | Срок хранения журнала в днях: по умолчанию `365`, допустимо от `1` до `36500`. Старые события удаляются автоматически. |
| `TUNNELSLATE_STATS_RETENTION_DAYS` | Срок хранения подробной статистики VPN в днях: по умолчанию `90`, допустимо от `1` до `36500`. Накопленные итоги устройств, клиентов и сервера не сбрасываются. |
| `TUNNELSLATE_TRUSTED_PROXIES` | Необязательный список адресов своих reverse proxy через запятую. Используется для IP в сессиях и защиты входа от перебора за nginx. Без него учитывается адрес прямого подключения; все пользователи одного прокси разделяют лимит. |

## Каталоги данных

В примере Compose используются каталоги `./data/app`, `./data/pki`, `./data/openvpn`, `./data/ccd` и `./data/control`. Чтобы перенести их, измените только пути слева в `volumes`; пути внутри контейнеров оставьте как в примере. Эти каталоги, `.env` и `docker-compose.yml` входят в резервную копию.

## Доступ к панели

### nginx и отдельный путь URL

nginx на хосте передаёт запросы на `http://127.0.0.1:8090`. Если изменили порт панели в Compose, измените его и в nginx.

Используйте [конфиг для отдельного домена](/deploy/nginx.conf.example) или [конфиг для пути /ovpn](/deploy/nginx.subpath.conf.example). Замените домен и пути к сертификатам, сохраните настройки обновления событий и передачи заголовков из примера.

Для `https://control.example.com/ovpn/` задайте:

```dotenv
TUNNELSLATE_PUBLIC_URL=https://control.example.com
TUNNELSLATE_BASE_PATH=/ovpn
TUNNELSLATE_COOKIE_SECURE=true
```

nginx должен передавать весь путь `/ovpn/`. Проверьте конфигурацию командой `nginx -t` и перезагрузите nginx.

### IP-адреса за nginx

В `TUNNELSLATE_TRUSTED_PROXIES` укажите адрес nginx, который видит приложение. При nginx на хосте это обычно Docker-шлюз:

```sh
docker inspect tunnelslate --format '{{range .NetworkSettings.Networks}}{{.Gateway}}{{end}}'
```

После изменения `.env` выполните `docker compose up -d`. Переданные IP принимаются только от доверенных прокси; используйте конкретные адреса или необходимые диапазоны.

### Локальная проверка без nginx

В `.env` задайте:

```dotenv
TUNNELSLATE_PUBLIC_URL=http://localhost:8090
TUNNELSLATE_BASE_PATH=
TUNNELSLATE_COOKIE_SECURE=false
```

Выполните `docker compose up -d` и откройте `http://localhost:8090` на сервере. Для доступа с другого компьютера запустите на нём:

```sh
ssh -N -L 8090:127.0.0.1:8090 user@server
```

Замените `user@server` своими данными и откройте `http://localhost:8090` в браузере на этом компьютере.

## Учётные записи и профили

Дополнительных администраторов создают в **«Учётных записях»**. Каждый получает одноразовый пароль для первого входа. Встроенного `admin` можно переименовать или заменить другой учётной записью.

Пароль первой учётной записи находится в `/data/app/initial_admin_password` внутри контейнера панели; при стандартных путях — в `./data/app/initial_admin_password` на хосте. После установки постоянного пароля файл удаляется. Перезапуск контейнера не сбрасывает пароль.

Чтобы клиент мог скачивать профили самостоятельно, создайте ссылку в его карточке. Скопируйте её до закрытия окна — ссылка показывается один раз. Передавайте её как пароль.

## Защита входа от перебора

Защита включена автоматически. Пять ошибок пароля или кода TOTP с одного IP за последние 15 минут блокируют новые входы с этого адреса на 15 минут, начиная с пятой ошибки. Попытки с разными именами пользователей суммируются. Успешные входы не добавляют ошибок и не сбрасывают уже накопленные. Повторные запросы во время блокировки не продлевают её.

Панель показывает оставшееся время ожидания. Блокировка сохраняется при перезапуске контейнера; после окончания срока вход разрешается автоматически. Истёкшие ошибки и блокировки удаляются. Начало блокировки записывается в журнал как **WARNING**, с IP-адресом; каждый последующий запрос отдельного события не создаёт.

Блокируются только новые входы с этого IP, в том числе завершение входа с TOTP. Действующие сессии администраторов, VPN-соединения и клиентские ссылки продолжают работать. Администратор может войти с другого адреса. Смена или аварийный сброс пароля не снимают блокировку IP.

За nginx обязательно настройте `TUNNELSLATE_TRUSTED_PROXIES`, чтобы учитывались адреса пользователей. Приложение принимает переданные IP только от доверенных прокси. Указывайте их конкретные адреса или необходимые диапазоны; не доверяйте всем адресам подряд. Администраторы за одним офисным NAT разделяют лимит.

Отдельно действует ограничение частоты всех запросов к входу и проверке TOTP: суммарно до 60 запросов за 5 минут с одного IP, включая успешные и некорректно оформленные. Оно защищает приложение от нагрузки и также возвращает временный отказ при превышении. TOTP дополнительно сохраняет собственное ограничение попыток на учётную запись.

## Двухфакторный вход с TOTP

По умолчанию TOTP отключён. Каждый администратор может настроить его для своей учётной записи:

1. Откройте **«Учётные записи»** и нажмите **«Настроить TOTP»** рядом со своим именем.
2. Введите текущий пароль. Отсканируйте появившийся QR-код в приложении-аутентификаторе или введите ключ вручную.
3. Введите шестизначный код из приложения и нажмите **«Включить TOTP»**.

До подтверждения кодом второй фактор не включается. Настройку нужно завершить за 10 минут. После включения остальные сессии вашей учётной записи завершатся, текущая останется открытой.

При следующих входах сначала введите пароль, затем код из приложения. Подтвердить вход нужно за пять минут. Код меняется каждые 30 секунд и принимается только один раз: если он уже использован, дождитесь следующего. На телефоне и сервере должно быть правильно настроено время.

Чтобы отключить второй фактор, нажмите **«Отключить TOTP»** у своей учётной записи и подтвердите действие текущим паролем и кодом. Остальные сессии этой учётной записи завершатся. Настройки других администраторов не изменятся.

Ключ шифрования TOTP создаётся автоматически в `data/app/totp.key`. Он уже входит в каталог постоянных данных: сохраняйте его вместе с БД. Восстановления одной БД без этого файла недостаточно для проверки кодов.

## Если потерян пароль администратора

Доступ можно восстановить из терминала сервера, даже если войти в панель больше некому. Контейнер панели должен быть запущен. Удалять данные или перезапускать VPN не нужно.

Чтобы сбросить пароль существующей учётной записи, замените `username` её именем:

```sh
docker exec -it tunnelslate reset-password username
```

Либо создайте нового администратора:

```sh
docker exec -it tunnelslate create-admin new-admin
```

Команда покажет имя учётной записи и новый одноразовый пароль прямо в терминале. Войдите с ними в панель и установите постоянный пароль. До его установки остальные разделы недоступны; если закрыть страницу, одноразовый пароль продолжит действовать.

При сбросе прежний пароль сразу перестаёт работать, а все сессии этой учётной записи завершаются. Сессии других администраторов сохраняются. Если при создании имя уже занято или при сбросе учётная запись не найдена, команда сообщит об этом и ничего не изменит. Имена не различаются по регистру; для новой учётки используйте 3–64 символа: латинские буквы, цифры, точку, дефис или подчёркивание, начиная с буквы или цифры. Имя `system` зарезервировано.

Пароль не записывается в журнал или в файл первоначального пароля — сохраните вывод команды и безопасно передайте его владельцу. Если вывод потерян, выполните сброс ещё раз. Сами операции отмечаются в журнале действий от имени `system:console`.

### Если потерян доступ к приложению-аутентификатору

Сброс пароля сохраняет TOTP. Чтобы отдельно отключить потерянный второй фактор, выполните:

```sh
docker exec -it tunnelslate reset-totp username
```

Все сессии этой учётной записи завершатся, пароль останется прежним. Войдите с ним и настройте TOTP заново. Если потеряны и пароль, и приложение-аутентификатор, выполните обе команды: `reset-totp` и `reset-password`. Сброс TOTP также фиксируется в журнале от имени `system:console`.

## Дальнейшие изменения и обновления

VPN-настройки меняются в панели. Подробное описание всех полей, индивидуальных настроек устройств и примеры изоляции и site-to-site собраны в [руководстве по настройкам OpenVPN](/docs/OPENVPN_SETTINGS_ru.md).

Применение общих настроек перезапускает OpenVPN и прерывает подключения. После изменения внешнего адреса, порта, протокола, MTU или MSS нужно скачать и импортировать профили заново; для DNS и маршрутов обычно достаточно переподключения.

### Переход с тестовой установки до первого релиза

Для первого релиза база создаётся по единой начальной схеме. Базы из предыдущих тестовых сборок с ней несовместимы: при запуске приложение выдаст понятную ошибку и не станет пересоздавать их автоматически.

Если у вас уже была такая тестовая установка, сохраните её отдельно и начните с пустых каталогов данных. Для стандартных путей из примера:

```sh
docker compose down
mv data data.pre-release-backup
docker compose up -d
```

Выберите свободное имя для резервного каталога. Если пути в `volumes` изменены, сохраните и замените пустыми все пять каталогов: `app`, `pki`, `openvpn`, `ccd` и `control`. Файлы `.env` и `docker-compose.yml` оставьте на месте. Одного удаления SQLite-файла недостаточно для чистой установки.

Затем повторите вход и настройку VPN по [шагам 4–5 быстрого старта](/docs/QUICKSTART_ru.md#4-войдите-в-панель). Учётные записи, настройки, клиенты и статистика старой тестовой установки не переносятся; для новой PKI понадобятся новые профили `.ovpn`.

### Обновление приложения и сохранение данных

После правок `.env` или Compose снова выполните `docker compose up -d`.

Для обновления исходников из Git:

```sh
git pull --ff-only
docker compose up -d
```

При обновлении совместимого релиза предварительно сохраните данные. Свои `.env`, `docker-compose.yml` и каталоги с данными оставляйте на месте. Если изменились примеры Compose или nginx, перенесите нужные изменения в локальные настройки. Для установки из архива замените исходники новой поставкой и выполните ту же команду запуска.

В резервную копию должны входить все каталоги данных и ваши локальные настройки. БД и сертификаты нужно восстанавливать из одной согласованной копии, сохраняя права доступа. При копировании файлов SQLite безопаснее остановить приложение; если копируете работающую БД, нужен способ резервного копирования, учитывающий её журнал записи. Отдельного контейнера для бэкапов нет.

Если очистить данные, следующий запуск станет новой установкой с новым администратором и сертификатами. Старые профили не смогут подключаться к новой установке.

## Установка DCO на хосте

DCO ускоряет обработку VPN-трафика средствами ядра хоста. По умолчанию выбран режим **«Автоматически»**: если драйвер или настройки не подходят, OpenVPN работает обычным способом. Панель показывает фактическое состояние DCO в обзоре сервера и вкладке «Соединение и DNS». Режим **«Выключено»** принудительно отключает ускорение.

Для DCO с OpenVPN 2.7 нужен модуль `ovpn` на Docker-хосте. Он входит в upstream Linux начиная с 6.16, если включён в сборку ядра; для старых ядер есть [ovpn-backports](https://github.com/OpenVPN/ovpn-backports). Установки пакета внутри контейнера недостаточно. Приложение не устанавливает и не загружает модули хоста: их подготовка выполняется отдельно. Изменение DCO, лимита подключений и keepalive не требует скачивать профили заново.

Этот шаг необязателен: без драйвера VPN работает обычным способом. Для OpenVPN 2.7 нужен именно `ovpn`; старый `ovpn-dco` предназначен для OpenVPN 2.6.

Если ядро уже содержит драйвер, достаточно загрузить его:

```sh
sudo modprobe ovpn
```

Если модуль не найден, установите бэкпорт для своего дистрибутива. Ниже — вариант для Rocky Linux 9 и совместимых систем с обычным ядром. Для других систем используйте [инструкции OpenVPN](https://community.openvpn.net/Pages/OpenVPN%20software%20repos).

```sh
sudo dnf install epel-release dnf-plugins-core
sudo dnf copr enable @OpenVPN/openvpn-release-2.7
sudo dnf install --setopt=install_weak_deps=False \
  "kernel-devel-$(uname -r)" \
  "kernel-devel-matched-$(uname -r)" \
  kmod-ovpn
```

Несмотря на название, этот пакет `kmod-ovpn` использует DKMS: драйвер собирается для ядра хоста. `kernel-devel` и `kernel-devel-matched` должны соответствовать выводу `uname -r`. Перед подтверждением установки проверьте список пакетов: для подготовки драйвера к уже работающему ядру установка нового ядра не требуется.

Если точной версии пакетов нет в текущем репозитории, найдите её в официальном архиве своего дистрибутива. Для Rocky это [Rocky Linux Vault](https://download.rockylinux.org/vault/rocky/): пакеты находятся в `AppStream/<архитектура>/os/Packages/k/` соответствующего выпуска. Скачайте оба RPM для работающего ядра и установите их вместе с драйвером из каталога загрузки:

```sh
sudo dnf install --setopt=install_weak_deps=False --setopt=localpkg_gpgcheck=True \
  "./kernel-devel-$(uname -r).rpm" \
  "./kernel-devel-matched-$(uname -r).rpm" \
  kmod-ovpn
```

Проверьте сборку и загрузите модуль:

```sh
sudo dkms autoinstall -k "$(uname -r)"
dkms status
sudo modprobe ovpn
lsmod | grep '^ovpn'
```

В `dkms status` для текущего ядра должно быть состояние `installed`. При включённом Secure Boot модулю также нужна подпись ключом, которому доверяет система; порядок настройки зависит от дистрибутива.

Чтобы загружать проверенный модуль при запуске хоста:

```sh
printf 'ovpn\n' | sudo tee /etc/modules-load.d/ovpn.conf > /dev/null
```

В панели выберите **«Соединение и DNS → DCO → Автоматически»** и примените настройки. Если этот режим уже выбран, перезапустите VPN-контейнер — существующие подключения прервутся:

```sh
docker compose restart tunnelslate-vpn
```

Через несколько секунд в панели должно появиться **«DCO: Работает»**. Дополнительная проверка:

```sh
docker compose exec tunnelslate-vpn \
  sh -c 'grep dco_enabled /run/openvpn/status.log'
```

Значение `1` означает, что работающий OpenVPN использует DCO; `0` — что не использует. Метка `[DCO]` в выводе версии означает только поддержку в сборке. Если модуль загружен, но ускорение не работает, посмотрите причину в панели и журнале VPN-контейнера.

После обновления ядра проверьте наличие соответствующего `kernel-devel`, успешную сборку DKMS и загрузку `ovpn` для новой версии. Отключить использование ускорения можно в панели, выбрав DCO **«Выключено»**.

## Внешняя аутентификация VPN

По умолчанию подключение остаётся по сертификату. Провайдеры LDAP/RADIUS настраиваются через панель, переменных `.env` для них нет. Сертификат можно дополнить внешним паролем для выбранных клиентов и устройств. [Порядок настройки и ограничения](/docs/VPN_AUTH_ru.md).

Для провайдеров появляется ключ `data/app/vpn-auth.key`. Он должен сохраняться вместе с БД, как и `totp.key`.

## Настройки панели и мониторинг

В **Настройках панели** можно изменить название инстанса и включить Prometheus-метрики. По умолчанию endpoint выключен. Для защищённого сбора доступен mTLS; сертификаты задаются файлами или через панель. [Настройка мониторинга, Grafana и оповещений](/docs/MONITORING_ru.md).
